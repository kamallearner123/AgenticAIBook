Session 5.0

Day 5: Structuring Outputs & LLM Specialist Behavior

Problem Statement: By default, an LLM talks like a generic, polite chatbot — it replies in free-flowing paragraphs and tries to be helpful about almost anything. But most real use cases need something more specific: feeding the model's output into another program, filling in a report template, or having it act like a focused specialist for one particular job. That means the model needs to (a) behave like a narrow specialist instead of a generalist, and (b) reply in a predictable, specific format instead of free text. How do you get both, reliably?

5.1. System Prompts vs. User Prompts

When you call an LLM through an API, you don't send a single block of text — you send a list of messages, and each message is tagged with a role. Two roles matter most for this lesson: "system" and "user".

  • The system message sets standing instructions for the whole conversation — who the model should act as, what it should focus on, and how it should behave. It's set once, usually before the conversation starts.
  • The user message is the actual question or task — the thing the person (or program) is asking the model to do right now.
system_and_user_messages.py 

# Program 5.0-1: A Minimal System + User Message List
messages = [
    {"role": "system", "content": "You are a helpful assistant that only answers questions about cooking."},
    {"role": "user", "content": "What's a good substitute for butter in a cake recipe?"}
]
Program 5.0-1: A System Message Sets the Rules, a User Message Asks the Question
Line by line:
  • messages is just a Python list — each item is one message in the conversation.
  • The first dictionary has "role": "system" — this is the standing instruction: "only answer questions about cooking."
  • The second dictionary has "role": "user" — this is the specific question being asked right now.
  • This list is what actually gets sent to the LLM API in a chat completion call.
This connects to something you already saw in Day 3: conversation_history.append({"role": "user", ...}). You were already using the "user" role there — now you know there's also a "system" role, and what it's for.

5.2. The Anatomy of a Specialist Persona

When an LLM is prompted with no persona at all, it defaults to being a generic, polite, all-purpose assistant. To make it behave like a focused specialist — for one job, on one kind of task — you build a persona out of four parts:

1. IDENTITY:
"You are a friendly Python mentor who reviews code written by beginners."
2. FOCUS / DOMAIN:
"Focus only on Python syntax, readability, and common beginner mistakes."
3. GUARDRAILS:
"Don't rewrite the whole program — suggest small, specific improvements. If the code isn't Python, say so."
4. OUTPUT FORMAT:
"List each suggestion as a short bullet point."
Figure 5.0-1: The Four Building Blocks of a Specialist Persona
What each part is doing:
  • Identity: Tells the model who to act as — this shapes its tone and vocabulary.
  • Focus / Domain: Narrows what the model should actually pay attention to, so it doesn't wander off-topic.
  • Guardrails: Sets boundaries — what the model should refuse or avoid doing.
  • Output Format: Tells the model how its answer should be shaped, not just what it should say.

5.3. Specialist Persona in Action

Let's see this persona actually change how the model responds. Here's a system persona for a beginner-friendly Python code reviewer, paired with a real user task:

python_code_review_persona.py 

# Program 5.0-2: Specialist Persona in Action
from openai import OpenAI

client = OpenAI()

system_persona = """
You are a friendly Python mentor who reviews code written by beginners.

FOCUS:
- Point out syntax errors, naming issues, and common beginner mistakes.
- Explain *why* something is a problem, not just what to change.

GUARDRAILS:
- Keep feedback encouraging and specific -- avoid vague comments like "make it better."
- If the code isn't Python, say so and don't attempt to review it.

TONE:
- Simple, plain language. Avoid jargon a beginner wouldn't know yet.
"""

user_code = """
def add_numbers(a, b):
    result = a+b
    return(result)

print(add_numbers(5, "3"))
"""

response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "system", "content": system_persona},
        {"role": "user", "content": f"Review this code:\n{user_code}"}
    ]
)

print(response.choices[0].message.content)
Program 5.0-2: A Persona Shapes Both What the Model Says and How

Notice what each part of the persona is actually doing:

  • The TONE block is a tone instruction — it stops the model from writing a wall of formal jargon a beginner can't follow.
  • The FOCUS block is a scope limit — it keeps the model from drifting into unrelated advice (style opinions, unrelated libraries, performance micro-optimizations).
  • The line "If the code isn't Python, say so" is a refusal rule — it tells the model exactly what to do when a request falls outside its job.

5.4. Persona Examples Across Different Jobs

The same four-part pattern applies to almost any specialist job you'd want an LLM to do. Here are two common, relatable examples:

Persona Goal One Guardrail Expected Output Shape
Customer Support Assistant Answer customer questions about orders, shipping, and returns. Never promise a refund or discount — only explain the policy and escalate to a human for exceptions. A short, polite paragraph in plain customer-facing language.
Meeting Notes Summarizer Turn a raw meeting transcript into a short, readable summary. Never invent action items or decisions that weren't actually said in the transcript. A short "Summary" paragraph followed by a bulleted "Action Items" list.

5.5. Why "Please Reply in JSON" Isn't Enough

Once you have a persona, the next problem is getting output your program can actually use. It's tempting to just ask nicely: "please reply in JSON." The trouble is, the model may still wrap that JSON in explanatory text or markdown code fences — and simple parsing code will crash the moment it hits anything that isn't pure JSON.

View: What Breaks When You Just Ask Nicely
asking_nicely_for_json.py 

# Program 5.0-3A: Asking Nicely for JSON (No Real Schema)
prompt = "Review this code and reply with JSON: { 'status': 'ok', 'score': 10 }"
res = call_llm(prompt)

# Often fails with JSONDecodeError, because the model may add
# markdown fences: ```json\n{ ... }\n```
# or a conversational lead-in: "Sure! Here is your JSON:"
import json
data = json.loads(res)  # Crash!
Program 5.0-3A: Extra Text Around the JSON Breaks Naive Parsing

The problem isn't that the model "got the JSON wrong" — the content might be perfectly correct. The problem is the extra text around it, which a plain-language instruction can't reliably prevent.

5.6. Structured Outputs: Guaranteeing the Format You Need

A schema is simply a description of exactly which fields you want in the output, and what type each field should be (text, number, a fixed set of choices, etc.). Instead of describing the format in a sentence, you describe it as a schema — and the API enforces it directly, rather than just hoping the model follows your instructions.

structured_output_with_pydantic.py 

# Program 5.0-3: Guaranteed Structured Output with Pydantic
from pydantic import BaseModel
from typing import Literal
from openai import OpenAI

class SupportTicket(BaseModel):
    customer_name: str
    issue_summary: str
    urgency: Literal["Low", "Medium", "High"]

client = OpenAI()

completion = client.beta.chat.completions.parse(
    model="gpt-4o-mini",
    messages=[
        {"role": "system", "content": "You extract structured ticket data from customer messages."},
        {"role": "user", "content": "Hi, my order #4521 hasn't arrived in 2 weeks and I need it urgently for a gift."}
    ],
    response_format=SupportTicket
)

ticket: SupportTicket = completion.choices[0].message.parsed
print(ticket.customer_name, ticket.issue_summary, ticket.urgency)
Program 5.0-3: A Flat Pydantic Schema Guarantees the Fields You Asked For

What a schema buys you: the API won't let the model return something that doesn't fit — no missing fields, no extra commentary, no "urgency": "super urgent!!" instead of one of your three allowed values. You get back an object your program can use directly, with no fragile text-parsing step in between.

5.7. Structured Output Beyond JSON

JSON isn't the only structured format. When a human will read the output — not a program — a markdown table, a numbered list, or a set of fixed labeled fields is often clearer, and doesn't need a Pydantic schema at all — just clear formatting instructions in the prompt.

Prompt: "Summarize these three product reviews as a markdown table with columns: Product, Rating, Key Complaint."
| Product | Rating | Key Complaint |
|---|---|---|
| Headphones | 3/5 | Battery drains fast |
| Keyboard | 5/5 | None |
Prompt: "Extract the invoice details as labeled fields: Name, Date, Amount."
Name: Acme Corp
Date: 2026-03-04
Amount: $1,250.00
Figure 5.0-2: Two Human-Readable Structured Formats — A Table and Labeled Fields

5.8. How the Model Actually Guarantees the Format

You don't need to build this yourself, but it's good to know what's happening under the hood: when you use a real structured-output feature (like response_format with a schema), the API doesn't just politely ask the model to follow your schema — at each generation step, it only allows the model to pick from the tokens that would keep the output valid according to your schema. That's why it becomes mathematically impossible for the model to produce broken JSON when structured outputs are actually enabled — very different from the "please reply in JSON" approach from Section 5.5, which is just a hopeful instruction.

5.9. Real-World Walkthrough: From Messy Input to Clean Output

Let's put 5.1–5.7 together on one realistic scenario: turning a messy customer support email into clean, structured data a program can act on.

Stage 1 — The raw, messy input:

"hii so i ordered the blue backpack last week (order #8834) but it still hasnt shipped??? i need it before friday for a trip, can someone please check whats going on this is kind of urgent thanks"

Stage 2 — The persona + schema used to process it:

messy_email_to_structured_ticket.py 

# Program 5.0-4: From Messy Email to Clean Structured Output
from pydantic import BaseModel
from typing import Literal
from openai import OpenAI

class SupportTicket(BaseModel):
    order_number: str
    issue_summary: str
    urgency: Literal["Low", "Medium", "High"]

client = OpenAI()

system_persona = """
You are a support ticket extraction specialist. Read the customer's message
and pull out only the facts needed to fill the SupportTicket schema.
Do not add information that wasn't stated in the message.
"""

customer_email = """
hii so i ordered the blue backpack last week (order #8834) but it still
hasnt shipped??? i need it before friday for a trip, can someone please
check whats going on this is kind of urgent thanks
"""

completion = client.beta.chat.completions.parse(
    model="gpt-4o-mini",
    messages=[
        {"role": "system", "content": system_persona},
        {"role": "user", "content": customer_email}
    ],
    response_format=SupportTicket
)

ticket: SupportTicket = completion.choices[0].message.parsed
print(ticket.model_dump_json(indent=2))
Program 5.0-4: Persona + Schema Turn Free Text Into a Reliable Object

Stage 3 — The clean, structured output:

{
  "order_number": "8834",
  "issue_summary": "Order has not shipped yet; customer needs it before Friday.",
  "urgency": "High"
}

The persona kept the model focused on extraction (not customer service chit-chat), and the schema guaranteed the result came back as three specific, correctly-typed fields — ready to hand to another program, with no fragile text-parsing step in between.

Assignment 5: Persona Guardrail Test

Task: Take the Customer Support Assistant persona from Section 5.4. Send it three test messages: one clearly in scope, one that tries to get it to promise a discount, and one completely unrelated question. Record how it responds to each, and adjust the guardrail wording if it doesn't hold up.
